# 0004. SQLite を共有し、キューを使わない

- ステータス: 採用
- 日付: 2026-10-08
- 関連: #2

## 背景

API で登録した予約を、ワーカーが販売開始前に受け取る必要がある。利用者は 1 人で、同時に動く予約もせいぜい数件。

## 決定

API とワーカーは同じ SQLite ファイル（WAL モード）を読み書きする。予約の受け渡しは `reservations.status` で行い、メッセージキューは使わない。

- API が `pending` で登録する
- ワーカーは `UPDATE ... SET status = 'preparing' WHERE id = ? AND status = 'pending'` で予約を取る（更新できた 1 件だけが処理する）
- マイグレーションは API の起動時に適用する。ワーカーは必要なマイグレーションが適用済みかだけを確認する

## 理由

- 個人利用の規模では、キューやサーバー型 DB の運用コストに見合わない
- 1 ファイルなのでバックアップや持ち運びが簡単

## 検討した他の案

- Redis / NATS などのキュー: 運用する物が増える
- PostgreSQL: 将来、複数台で動かすなら検討する。今は不要

## 影響

- 書き込みが同時に起きると待たされる（`busy_timeout = 5000`）。購入の最中には DB へ書かない（[0011](0011-worker-polling-and-timing-buffer.md)）
- 複数台で動かす必要が出たら、この ADR を見直す
