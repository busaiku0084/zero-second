# 0011. ワーカーはポーリングで予約を取り、計測値はまとめて書く

- ステータス: 採用
- 日付: 2026-10-09
- 関連: #4

## 背景

ワーカー（striker）は、API が登録した予約を販売開始の少し前に受け取り、時刻に合わせて購入する。DB は SQLite を共有している（[0004](0004-shared-sqlite-without-queue.md)）。

## 決定

- **予約の取得**: 一定間隔（既定 1 秒）で DB をポーリングし、`mode = 'auto'`・`status = 'pending'`・販売開始の `STRIKER_LEAD_MS`（既定 120 秒）前を過ぎた予約を取る。`pending → preparing` の条件付き更新で取ったものだけを処理する
- **1 件の流れ**: `login` → `prepare` → 時刻合わせ → 販売開始まで待機 → `running` → `purchase` → 結果を保存
- **待機**: 目標時刻の少し前まで `tokio::time::sleep` で眠り、最後の数ミリ秒はビジーウェイトで合わせる
- **時刻合わせ**: サイトが用意したエンドポイントのレスポンスの `Date` ヘッダーと往復時間から、サーバー時刻とのずれを推定する（NTP と同じ考え方）
- **計測値**: リクエストごとの計測値はメモリに溜め、購入が終わってからまとめて `timings` に書く。購入の最中に DB へ書かない
- **再試行**: 回数と間隔に上限を設ける（`RetryPolicy`）。売り切れと、人の対応が必要な状態（CAPTCHA・待機列・購入上限）は再試行しない
- **対応サイト**: ワーカー側にも登録済みアダプタの一覧を持ち、一覧にないサイトの予約は `failed` にして処理しない

## 理由

- 個人利用で予約は少なく、1 秒間隔のポーリングで十分間に合う（取り出しは販売開始の 2 分前）
- 購入の瞬間に DB のロック待ちが入らないようにする
- 規約で禁止されたサイトを、API 以外の経路（DB の直接編集など）からも動かさないため

## 検討した他の案

- API からワーカーへ通知（HTTP / キュー）: 構成が増える。ポーリングで遅れが問題になったら検討する
- 計測値を 1 件ずつ書く: 実装は単純だが、購入の最中に書き込み待ちが入りうる

## 影響

- 予約を登録してから販売開始まで 2 分を切っている場合、取り出した直後に準備を始める
- ワーカーが落ちて `preparing` / `running` のまま残った予約は、起動時に `failed` に戻す（骨格では TODO）
