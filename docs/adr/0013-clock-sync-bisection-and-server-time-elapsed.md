# 0013. 時刻合わせは秒の切り替わりを二分探索し、所要時間はサーバーの時計で測る

- ステータス: 採用
- 日付: 2026-10-09
- 関連: #4、#19、[ADR 0007](0007-time-representation.md)、[ADR 0011](0011-worker-polling-and-timing-buffer.md)

## 背景

ワーカーは HTTP の `Date` ヘッダーからサーバー時刻とのずれを測り、販売開始の瞬間に送る。`Date` は秒単位（切り捨て）なので、1 回の往復からは最大 ±500ms の誤差が出る。

モックサイトで通しで動かしたところ、同じマシンなのに -304ms / -471ms のずれと測られ、そのぶん購入が遅れて所要時間が 0.5 秒前後に膨らんだ。

また所要時間を「完了時刻（端末の時計）− 販売開始（サイトの時計）」で出していたため、端末とサイトの時計がずれていると値が狂う（ずれ +1.2 秒では所要時間が負になった）。

## 決定

- ずれの範囲 `[lo, hi)` を持ち、応答ごとに `[Date − 受信時刻, Date + 1000 − 送信時刻)` との共通部分に狭める（`clock::OffsetBounds`）
- 2 回目以降は、ずれが範囲の中央だとしたときにサーバーで秒が切り替わる瞬間に届くよう送信時刻を選ぶ（二分探索）。最大 8 回、範囲が往復時間（最低 10ms）まで狭まったら止める
- 時刻合わせは販売開始の 500ms 前までに終える。間に合わなければ、その時点の範囲の中央を使う
- 所要時間は `完了時刻 + clock_offset_ms − 販売開始` とする（API の `lib/rows.ts` の `elapsedMs`）。ずれを測っていない実行（手動購入など）は 0 とみなす

## 理由

- 応答 1 回ごとに範囲がほぼ半分になるので、8 回（約 8 秒）で 1 秒の幅が数 ms + 往復時間まで狭まる。ローカルのモックで、+1234ms のずれを 1241ms と測れた
- 範囲の共通部分を取る方法は、往復時間の揺れがあっても真の値を外さない（矛盾する応答は捨てる）
- 販売開始はサイトの時計で決まるので、所要時間もサイトの時計にそろえないと比べられない

## 検討した他の案

- 何回か送って往復時間が最短の回を使う（骨格での実装）: 秒の切り捨ての誤差が残る
- NTP で端末の時計を合わせる: 端末の時計が合っていても、サイトのサーバーの時計がずれていれば意味がない
- 所要時間を端末の時計のまま出す: 時計のずれがそのまま所要時間に混ざる

## 影響

- 時刻合わせに最大 8 秒ほどかかる。販売開始の 2 分前（`STRIKER_LEAD_MS`）から準備するので通常は問題ない。直前に登録した予約では精度が落ちる
- 時刻合わせのリクエストが `timings` に最大 8 件残る（phase は `clock`）
- `Date` ヘッダーを返さないサイトでは、ずれは測れず端末の時計を使う

## 追記（#36）

ブラウザ操作モード（ADR 0021）では、ログインや注文情報の入力を販売開始の約 2 分前に済ませるので、その段階で失敗した実行は販売開始より前に終わる。
これを上の式で計算すると所要時間がマイナスになるため、結果が負になる実行は所要時間なし（`null`）とする。
