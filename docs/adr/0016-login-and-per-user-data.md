# 0016. ID とパスワードでログインし、データはユーザーごとに分ける

- ステータス: 採用
- 日付: 2026-10-09
- 関連: #25、[ADR 0008](0008-credential-encryption.md)、[ADR 0009](0009-server-side-data-access.md)、[ADR 0015](0015-docker-and-port-range.md)

## 背景

これまでは画面を開ければ誰でも使え、データも 1 人分しかなかった。何人かで使えるようにしたい。
外部サービスに依存せず、ローカル・Docker だけで完結することが前提（ADR 0015）。

## 決定

### ログイン
- **ID + パスワード**をアプリの中で管理する。パスワードは `node:crypto` の scrypt（N=2^15, r=8, p=1、ソルト 16 バイト）でハッシュ化し、`scrypt$logN$r$p$salt$hash` の形で `users.password_hash` に保存する
- **セッションは DB に持つ**。ランダムな 256 bit のトークンを発行し、DB にはその SHA-256 だけを保存する。有効期限は 30 日。パスワードを変えると、ほかのセッションは消す
- web はトークンを HttpOnly・SameSite=Lax の Cookie（`zs_session`）に入れ、API を呼ぶときに `x-session-token` ヘッダーで渡す。ブラウザから API へは直接つながない（ADR 0009）
- **API が毎回セッションを確かめる**（認可の判断は API の 1 か所）。公開のルート（`/health`・`/auth/login`・`/auth/setup`・`/auth/invitations/:token`）以外は、許可リスト方式ですべてログイン必須にする
- web の `proxy.ts` は Cookie の有無だけを見てログイン画面へ移す（楽観的なチェック）。セッションが無効なら、API が 401 を返し、`lib/api.ts` がログイン画面へ移す
- ログインの失敗は、同じログイン ID で 15 分に 5 回まで（メモリ上。API の再起動で消える）。ID が無くても照合はして、応答時間と文言で ID の有無が分からないようにする

### ユーザーの追加
- **招待制**。最初のユーザーは `/setup` で作り、管理者（`admin`）になる。ユーザーが 1 人でもいれば `/setup` は使えない
- 管理者は招待リンクを作る。リンクのトークンは DB にハッシュだけを保存し、作ったときに 1 回だけ表示する。7 日で期限切れ、1 回だけ使える。未使用なら取り消せる
- 招待から登録したユーザーは `member`

### データの範囲
- **完全に分ける**。`accounts`・`reservations` に `user_id` を付け、API のクエリはすべて `user_id` で絞る。`runs`・`timings` は予約を通して絞る
- ほかのユーザーのデータは「見つからない」（404）として扱い、存在も分からないようにする
- **管理者もほかのユーザーの中身は見ない**。管理者だけが使えるのは、ユーザーの一覧と招待の管理
- サイトのアカウントの一意制約は `(user_id, site, login_id)`。同じログイン ID を別のユーザーが登録してもよい
- ログイン機能より前に登録したデータ（`user_id` が NULL）は、最初の管理者を作ったときにその人へ引き継ぐ

## 理由

- 外部サービス（OAuth・メール送信）が要らず、ローカル・Docker だけで動く
- 招待制にすると、うっかり公開しても知らない人が登録できない
- 認可を API に集めると、web のページを足しても確認が漏れにくい。web の Cookie の確認は表示の都合で、守りは API
- トークンや招待のハッシュだけを保存すれば、DB のファイルが漏れても、そのままログインや登録には使えない
- scrypt は `node:crypto` だけで使え、依存を増やさない（bcrypt・argon2 は native のパッケージが要る）

## 検討した他の案

- GitHub / Google のログイン（OAuth）: パスワードを持たずに済むが、OAuth アプリの登録とコールバック URL が要り、ローカルで完結しない
- メールのマジックリンク: SMTP などのメール送信が要る
- 誰でも登録できる: 公開したときに誰でも使えてしまう
- 署名つき Cookie（JWT など）だけでセッションを持つ: DB を見ずに確かめられるが、ログアウトやパスワード変更で無効にできない
- Auth.js などのライブラリ: 機能が多く、Hono（API）側でセッションを確かめる今の構成に合わせにくい

## 影響

- API の既存のルートはすべてセッションが必要になった。テストは管理者としてログインしたセッションで呼ぶ
- ワーカー（striker）はユーザーを意識しない。予約とアカウントの組み合わせは API が登録時に確かめている（本人のアカウントしか紐づけられない）。ログイン情報の復号（#4）を作るときも、予約とアカウントの `user_id` が同じかをワーカー側でも確かめる
- ログイン失敗の回数はメモリ上なので、API を複数台にするなら DB などに移す
- https で公開するときは `SESSION_COOKIE_SECURE=true` にする（既定は http://127.0.0.1 で使うため false）。招待リンクの URL は `APP_URL` で固定できる
- パスワードを忘れたときの再設定、ユーザーの削除・権限の変更は、まだ画面がない
