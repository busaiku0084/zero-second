# 0018. 画面のカウントダウンは、web サーバーの時計とのずれを測って補正する

- ステータス: 採用
- 日付: 2026-10-10
- 関連: #12、[ADR 0005](0005-respect-site-terms.md)、[ADR 0013](0013-clock-sync-bisection-and-server-time-elapsed.md)

## 背景

手で購入するときは、販売開始の瞬間に操作を始めたい。スマホや PC の時計は数百ミリ秒〜数秒ずれていることがあり、端末の時計そのままのカウントダウンでは出遅れたり早すぎたりする。
ブラウザからは NTP を直接使えない。チケットサイトの時刻（Date ヘッダー）を取りに行くのは、サイトへの自動アクセスになるのでしない（ADR 0005）。

## 決定

- web に `GET /api/time`（サーバーの現在時刻を返すだけ）を置き、ブラウザから 6 回続けて呼ぶ。1 回目は接続の確立が入るので捨てる
- 各回で「送る直前 t0・受け取った直後 t1（端末の時計）」と「サーバーの時刻」を記録し、往復時間がいちばん短い回で `ずれ = サーバー − (t0 + t1) / 2`、誤差は `±往復時間 / 2` とする（`lib/clock.ts`）
- 画面の中のカウントダウンは 1 回の測定を共有し、10 分ごとに測り直す。測れるまでは端末の時計のまま表示する
- 予約の詳細とランチャーに「端末の時計が 0.123 秒遅れています（±0.008 秒）」のように測った結果を出す
- サーバー（ホスト）の時計は OS の NTP で合っている前提にする
- ランチャー（`/reservations/:id/launch`）は、補正したカウントダウン・購入するもののメモ・公演ページを開くボタンをまとめた画面。公演ページは押したときにだけ開き、自動で開いたり再読み込みしたりはしない。3 秒前から音で知らせることはできる（音を出すにはボタンを押す必要がある）

## 理由

- web サーバーは常に使っていて、ログイン済みなら追加の設定なしに測れる。同じ LAN や localhost なら往復が数ミリ秒で、誤差も小さい
- 往復時間が最短の回を使うのは、ネットワークで待たされた回ほど真ん中の推定がずれるため（NTP と同じ考え方）
- チケットサイトにアクセスしないので、規約の線（ADR 0005）を越えない

## 検討した他の案

- チケットサイトの Date ヘッダーで測る（ワーカーと同じ ADR 0013 の方法）: サイトへの自動アクセスになるうえ、ブラウザからは CORS で読めない
- 外部の時刻 API（worldtimeapi など）: 外部サービスに依存し、往復も長い
- 補正しない: 端末の時計のずれがそのまま出遅れになる

## 影響

- ホストの時計がずれていると、補正もずれる。ワーカーの自動購入は ADR 0013 のとおりサイトの時計で測るので、この影響は受けない
- チケットサイト自体の時計とのずれは補正できない（サイトの時計がずれていれば、その分は残る）
