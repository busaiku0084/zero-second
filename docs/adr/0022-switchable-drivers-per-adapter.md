# 0022. 1 つのアダプタが API とブラウザ操作の両方を持ち、ワーカーの設定で切り替える

- ステータス: 採用
- 日付: 2026-10-10
- 関連: #42、[ADR 0012](0012-mock-site-as-local-http-server.md)、[ADR 0021](0021-browser-mode.md)

## 背景

ADR 0021 では、アダプタごとに操作の方法を 1 つ選ぶ（`TicketSite::driver()`）ことにした。
しかし同じサイトでも、API が変わった・API だけ混雑対策が厳しい・画面のほうが安定している、など、状況によって方法を変えたいことがある。
また、新しいサイトを足すときの見本が、API は mock、ブラウザ操作は Sauce Demo と別々のサイトに分かれていて、同じ購入の流れを 2 つの方法でどう書くかを比べにくかった。

## 決定

- `TicketSite::driver()` を **`drivers()`（対応する方法の一覧。先頭が既定）** に変える。両方に対応するアダプタは、login / prepare / purchase の中で **`ctx.driver`** を見て処理を分ける
- どちらを使うかは**ワーカーの中で決める**（予約の画面では選ばない）。既定はアダプタの `drivers()` の先頭で、環境変数 **`STRIKER_DRIVERS`**（例: `mock=browser`）で切り替える。登録されていないサイトや、アダプタが対応していない方法を指定したら起動時に止める
- ブラウザは `ctx.driver` が Browser のときだけ起動する
- 実行に使った方法を **`runs.driver`**（`http` / `browser`）に残し、実行結果の画面に出す
- **モックサイトに画面での購入を足し**（`/login` → `/events/:id` で席種・枚数を選ぶ → 購入 → `/orders/:id`）、mock アダプタを両方に対応させる。`sites/mock/api.rs` と `sites/mock/browser.rs` を、新しいサイトの骨格の見本にする（docs/development/adding-a-site.md）
  - 一般的なチケットサイトにある要素を入れる: CSRF トークン、複数の席種、1 回の注文の枚数の上限、売り切れ・CAPTCHA・混雑
  - 公演情報（`GET /api/events/:id`）はログインなしで読めるようにする
- 枚数の上限を超える予約は `HumanActionRequired` で止める（購入上限は回避しない）。ない席種は準備の段階で失敗にする

## 理由

- 方法の選択をアダプタの外（設定）に出すと、コードを変えずに切り替えて比べられる。予約の画面に出すと、使う人がサイトの作りを知っている必要があり、選び間違いも起きる
- 同じサイト・同じ段階で 2 つの方法を並べると、骨格として読みやすい。モックサイトは自分で用意したローカルのサイトなので、規約の線（ADR 0005）を気にせず作り込める

## 検討した他の案

- 予約ごとに方法を選ぶ: 画面が複雑になり、選び間違いで失敗する。比べたいときは設定で足りる
- API で失敗したら自動でブラウザ操作に切り替える: 販売開始の瞬間にブラウザを起動・ログインし直すことになり遅い。準備の段階で決めておく必要がある
- アダプタを方法ごとに 2 つに分ける（`mock-http` と `mock-browser`）: サイトの id と sites.json が方法の数だけ増え、予約のサイトの選択に方法が混ざる

## 影響

- アダプタは対応する方法ごとに login / prepare / purchase を書く。片方だけのアダプタは今までどおり（`drivers()` の既定は Http だけ）
- `STRIKER_DRIVERS` を変えたらワーカーを起動し直す
- mock アダプタで、予約の席種がモックサイトの席種（一般・前方エリア）と一致しないと準備で失敗するようになった
