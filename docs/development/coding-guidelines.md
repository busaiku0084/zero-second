# コーディングルール

zero-second のコードを書くときの決まりごと。CLAUDE.md は要点だけを載せ、詳細はここに書く。
迷ったら「周りのコードに合わせる」を優先し、このファイルにない判断をしたら追記する（大きな判断は ADR にする）。

## 1. 共通

### 命名
- 識別子は英語、コメント・ドキュメント・画面の文言は日本語
- 略語は避ける。広く通じるもの（`id`・`url`・`db`・`api`）だけ使う
- 時刻は `*_at_ms` / `*AtMs`、長さは `*_ms` / `*Ms`（[ADR 0007](../adr/0007-time-representation.md)）
- 真偽値は `is*` / `has*` / `*Allowed` など、読んで真偽と分かる名前にする

### コメント
- 「何をしているか」ではなく「なぜそうしているか」を書く。コードを読めば分かることは書かない
- 公開する関数・型には、用途が一目で分からなければ 1 行の説明を付ける
- `TODO` には issue 番号を付ける（`TODO(#12): ...`）。番号のない TODO は残さない

### エラー
- 握りつぶさない。`catch` したら、利用者に伝えるか、ログに残して上に投げる
- 利用者向けのエラー文言は「何が起きたか」と「どうすればよいか」を書く。謝罪や曖昧な表現（「エラーが発生しました」だけ）は避ける
- 想定外のエラーは、API では 500 とログ、Web では `error.tsx` に任せる

### セキュリティ・秘密情報
- パスワード・Cookie・トークン・HAR ファイルはコミットしない。ログ・テストのフィクスチャ・ドキュメントにも実値を書かない
- 外部からの入力（HTTP のリクエスト、フォーム、DB の直接編集）は境界で検証する
- SQL には必ずプレースホルダ（`?`）で値を渡す。文字列連結で SQL を組み立ててよいのは、列名など固定の候補から選ぶ場合だけ
- 利用規約で自動化が禁止されたサイトを動かす経路を作らない（[ADR 0005](../adr/0005-respect-site-terms.md)）

### 依存の追加
- 追加する前に、標準ライブラリや既存の依存で足りないか考える
- バージョンは公開から 2 週間以上たったものを選ぶ
- 何のために入れたかを PR に書く

## 2. TypeScript（共通）

- `strict` と `noUncheckedIndexedAccess` を前提に書く。`any` は使わない（外部入力は `unknown` で受けて zod で絞る）
- 型アサーション（`as`）は、DB の行を型に変換するなど理由がはっきりした場所だけに閉じ込める（例: `apps/api/src/lib/rows.ts`）
- `import type` を使い分ける（`verbatimModuleSyntax`）
- 共有パッケージ（`packages/shared`）内の import は拡張子なしで書く（Next.js のビルドで `.js` → `.ts` が解決されないため）
- Biome の警告 0 件を保つ。抑制コメントは理由を書いたうえで最小限にする
- 入力のスキーマ・API のレスポンス型・サイト一覧は `packages/shared` に置き、web と api で同じものを使う。サイト一覧の実体は `sites.json`（striker のテストも読む）

## 3. API（Hono）

- ルートは `apps/api/src/routes/` にリソースごとに置き、`app.ts` でまとめる
- 入力は `zValidator` と `validationHook` で検証し、失敗時は `{ error, issues: [{ path, message }] }` を 400 で返す
- ステータスコード: 作成 201、削除 204、見つからない 404、状態の衝突（実行中の予約の変更など）409、入力の誤り 400
- 複数のテーブルを更新するときはトランザクションにする（`BEGIN` / `COMMIT` / 失敗時 `ROLLBACK`）
- レスポンスにログイン情報を含めない
- ルートを追加したら `app.request()` を使った Vitest のテストを書く（正常系 1 つ以上と、主な失敗系）

## 4. Web（Next.js / React）

### データの流れ
- API はサーバー側からだけ呼ぶ（`lib/api.ts`）。更新は Server Actions（`app/actions.ts`）で行う（[ADR 0009](../adr/0009-server-side-data-access.md)）
- フォームは `useActionState` で状態を受け取り、エラー時は入力値を戻す（パスワードは戻さない）
- 取り消せない操作は `ConfirmButton` で 2 段階にする。ブラウザの `confirm()` は使わない

### コンポーネント
- 既定は Server Component。状態やブラウザの API が必要なものだけ `"use client"` にする
- 1 ファイル 1 コンポーネントを基本にし、名前とファイル名を揃える（`ReservationForm.tsx`）
- 日時の変換・表示は `lib/format.ts`、状態のラベルは `lib/labels.ts` を使う。コンポーネントの中で個別に書かない

### スタイル
- 色・書体・角丸・影は `app/globals.css` のトークン（CSS 変数）だけを使う。色を直書きしない
- トークンはライト（`:root`）とダーク（`prefers-color-scheme` と `[data-theme="dark"]` の両方）で定義する
- 余白は flex / grid の `gap` で取る。要素ごとの margin で調整しない
- 幅 400px 前後でも横スクロールが出ないこと。表は `.table-wrap` で包む
- 数字が縦に並ぶ所（表・時刻）は等幅数字（`.mono` / `td.num`）にする

### グラフ（[ADR 0010](../adr/0010-handmade-svg-charts.md)）
- 何を伝えるかで形を選ぶ。1 つの数字なら数値タイル、推移なら線、内訳なら積み上げ
- 色は `--series-1..3`（カテゴリ）。4 系列以上は「その他」にまとめる
- 線 2px、マーカーは半径 4px 以上で周りに 2px の縁取り、目盛り線は 1px の実線
- 二重軸は使わない
- 2 系列以上は凡例を出す。数値は要所（最後の点など）だけに直接ラベルを付ける
- ホバーとキーボードの両方で値を読めるようにし、表ビューに切り替えられるようにする
- 文字の色は系列の色ではなく、文字用のトークン（`--ink` / `--ink-2` / `--muted`）を使う

### アクセシビリティ
- 状態は色だけで伝えず、アイコン + ラベルを付ける（`StatusPill` / `ResultPill`）
- フォームの部品には `label` を付け、エラーは `aria-invalid` と文言で示す
- キーボードで操作でき、フォーカスが見えること
- 動きは `prefers-reduced-motion` で止められるようにする

### 文言
- 利用者から見た言葉で書く（「webhook 設定」ではなく「通知」）
- ボタンは何が起きるかを書く（「予約を登録」「記録ごと削除する」）
- 能動態・短い文で書く

## 5. Rust（striker）

- `cargo fmt` と `cargo clippy --all-targets -- -D warnings` が通る状態を保つ
- エラーは、サイトのアダプタでは `SiteError`、それ以外は `anyhow::Result` で返す。文脈は `.context()` で足す
- `unwrap()` / `expect()` はテスト以外で使わない
- 非同期の中で長くブロックしない。DB の操作は短いクエリに限り、購入の最中には DB へ書かない（[ADR 0011](../adr/0011-worker-polling-and-timing-buffer.md)）
- HTTP のリクエストは必ず `TimedClient` を通して計測する
- 再試行は `RetryPolicy` を使う。`SoldOut` と `HumanActionRequired` は再試行しない
- 時刻計算・再試行の判定などの純粋な関数には単体テストを付ける
- サイトのアダプタを追加するときは `.claude/skills/new-site-adapter` と `docs/development/adding-a-site.md` の手順に従う。アダプタは送り先のホストを設定で固定し、予約の公演 URL のホストへそのまま送らない

## 6. DB・マイグレーション

- スキーマの変更は `db/migrations/NNNN_name.sql` を追加して行う。適用済みのファイルは書き換えない
- 列の削除などの破壊的変更は避ける。SQLite で制約を変えるためにテーブルを作り直すときは、データを移す SQL を書き、移行のテストを付ける（例: `0002_manual_mode.sql` と `db.test.ts`）
- 先頭のコメントに、何のための変更かを書く
- 列の意味が名前で分からないときは SQL にコメントを書く
- スキーマを変えたら `docs/database.md` と、TS・Rust 両方の型を直す

## 7. テスト

- 実装と同じ場所に `*.test.ts` を置く（Vitest）。Rust は同じファイルの `#[cfg(test)] mod tests`
- テスト名は日本語で、何を確かめるかを書く（「規約で自動化が禁止されたサイトでは auto を選べない」）
- DB を使うテストはインメモリの SQLite にマイグレーションを当てて使う。テスト同士で状態を共有しない
- 外部のサイトにアクセスするテストは書かない。必要ならモックサイトか、記録したレスポンス（実値を伏せたもの）を使う
